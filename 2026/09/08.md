Luau

반복문 문제 풀이

Luau 문법에 익숙해지기 위해 정올 스타일의 문제를 직접 풀었다.

두 정수 A, B를 입력받아 두 수 사이의 구구단을 출력하는 문제를 작성하면서 숫자 입력, while, for문의 동작 방식을 다시 확인했다.

처음 작성한 코드에서는 다음과 같은 문제가 있었다.

while문의 조건은 존재하지만 A가 변경되지 않아 반복이 끝나지 않을 수 있음

for문의 시작값과 끝값이 의도한 구구단 범위와 다름

출력 형식과 반복 구조가 섞여 있음

문제를 수정한 뒤 실제 제출에서도 정답을 확인했다.

반복문의 종료 조건

이번 문제를 통해 반복문에서는 단순히 조건식을 작성하는 것뿐만 아니라

반복할 때 조건에 사용되는 값이 실제로 변하는가?

를 확인해야 한다는 점을 다시 배웠다.

조건 확인
    ↓
반복 실행
    ↓
조건에 영향을 주는 값 변경
    ↓
다시 조건 확인

이 과정이 없다면 조건이 계속 true로 유지되면서 무한 반복이 발생할 수 있다.

Roblox

기본 가챠 시스템 제작

Roblox에서는 Sol's RNG와 비슷한 구조를 이해하기 위해 간단한 가챠 시스템을 만들어봤다.

전체 구조는 다음과 같이 나눴다.

Client
  ↓ Roll 요청
RemoteEvent
  ↓
Server
  ↓
RollService
  ↓ 결과 생성
Server
  ↓
Client

클라이언트에서는 버튼이 눌렸을 때 서버에 Roll 요청만 보낸다.

실제 확률 계산과 결과 결정은 서버의 RollService가 담당한다.

RemoteEvent의 역할

클라이언트와 서버는 같은 코드에서 직접 값을 주고받는 것이 아니라 RemoteEvent를 사용한다.

사용한 흐름은 다음과 같다.

Client
FireServer()
    ↓
Server
OnServerEvent
    ↓
RollService.RollAura()
    ↓
FireClient()
    ↓
Client
OnClientEvent

이 구조를 통해 클라이언트는 요청을 보내고, 서버가 최종 결과를 결정한다는 Roblox의 기본적인 서버 권한 구조를 이해했다.

특정 결과를 전체 플레이어에게 전송

특정 희귀도인 Mystic이 등장했을 때는 해당 플레이어에게만 결과를 보여주는 것이 아니라 전체 플레이어에게 전달하도록 처리했다.

일반 결과
→ FireClient

특수 결과
→ FireAllClients

이를 통해 같은 RemoteEvent라도 상황에 따라 특정 플레이어 또는 전체 플레이어에게 이벤트를 전달할 수 있다는 점을 확인했다.

Today I Learned

1. 프로토타입은 구현된 기능을 실제 플레이에 넣어봐야 의미가 있다

Fireball과 Levitate가 각각 잘 동작하더라도 실제 스테이지에서 재미있는 상호작용이 만들어지는지는 별도로 확인해야 한다.

기능 구현 이후에는 가능한 빠르게 테스트 가능한 게임 형태로 만드는 것이 중요하다.

2. 반복문에서는 종료 조건뿐 아니라 값의 변화도 확인해야 한다

while 조건이 존재한다고 해서 자동으로 반복이 끝나는 것은 아니다.

조건에 사용되는 값이 반복 중 변화하지 않는다면 무한 반복이 발생할 수 있다.

3. Roblox에서는 서버가 중요한 결과를 결정해야 한다

가챠 결과처럼 게임에 영향을 주는 값은 클라이언트에서 직접 결정하는 것이 아니라 서버에서 처리하는 구조가 적절하다.

클라이언트는 입력과 표시를 담당하고, 서버는 판정과 상태를 담당하는 역할 분리가 중요하다.

한 줄 정리

오늘은 PLM의 핵심 기능 구현 상태를 점검해 스테이지 제작을 우선하기로 했고, Luau 문제 풀이와 Roblox 가챠 시스템 제작을 통해 반복문과 클라이언트-서버 구조를 학습했다.
