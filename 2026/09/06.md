# 🖥️ UIControllGame

## 🧩 Puzzle 03 — Program Path Puzzle

Puzzle 03의 목표는

> **여러 곳에서 얻은 단어 조각을 조합해 올바른 파일 경로를 만들고, 해당 프로그램을 찾아 삭제하는 것**

이다.

테스트용 목표 경로는

```text
KeyBoardBlock
```

으로 설정했다.

`targetPath`는 Inspector에서 변경할 수 있도록 만들어
이후 실제 퍼즐 경로로 쉽게 교체할 수 있게 했다.

---

## 📋 클립보드 데이터를 이용한 경로 조합

경로를 키보드로 직접 입력하는 것이 아니라
기존에 만들어둔 클립보드 시스템을 활용했다.

```text
CopyableUI
    ↓
ClipboardManager
    ↓
DraggableUI
    ↓
DropTarget
    ↓
ProgramPathPuzzle
```

플레이어가 복사한 단어를 `DraggableUI`로 가져와
경로 입력 영역인 `DropTarget`에 넣는다.

정상적으로 드롭되면 해당 Object ID를 받아
`currentPath`에 하나씩 추가하도록 구성했다.

---

## 🔒 잘못된 경로 입력 방지

경로 조각에는 퍼즐에서 허용하는 문자열만 들어와야 하기 때문에
`/` 또는 `\` 등이 포함된 잘못된 입력은 받지 않도록 처리했다.

즉 `DropTarget`에 무엇이든 넣을 수 있게 만드는 것이 아니라
Puzzle 03에서 사용할 수 있는 데이터인지 한 번 더 확인하도록 했다.

# 📁 파일 탐색기와 Puzzle 03 연결

Puzzle 03은 경로를 맞추는 것만으로 끝나는 퍼즐이 아니다.

최종 목표는

```text
경로 완성
    ↓
목표 프로그램 발견
    ↓
프로그램 종료
    ↓
파일 삭제
    ↓
Puzzle 03 Clear
```

이다.

따라서 기존에 구현해둔 `FileExplorerWindow`와
Puzzle 03을 직접 연결했다.

---

## 👁️ 정답 경로에서만 파일 표시

게임을 시작하자마자 삭제해야 할 파일이 보이면
경로를 완성하는 과정 자체가 의미가 없어진다.

그래서 대상 프로그램은 기본적으로 숨기도록 했다.

```text
Wrong Path
→ Target Program Hidden

Correct Path
→ Target Program Visible
```

`currentPath`가 `targetPath`와 정확히 일치했을 때만
목표 프로그램이 파일 탐색기에 나타나도록 했다.

테스트를 쉽게 하기 위해

* 현재 경로가 정답인지
* 대상 프로그램이 표시되고 있는지

를 bool 값으로 바로 확인할 수 있도록 구성했다.

---

## 🛑 실행 중인 프로그램 삭제 방지

경로를 맞춘 뒤 파일이 보이더라도
프로그램이 아직 실행 중이라면 바로 삭제할 수 없도록 했다.

```text
Target 발견
    ↓
프로그램 실행 중?
    ↓
YES → 삭제 불가
NO  → 삭제 가능
```

따라서 플레이어는 먼저 프로그램을 종료하고
그 다음 파일 탐색기에서 해당 파일을 삭제해야 한다.

이 과정이 Puzzle 03의 실제 해결 과정이 된다.

---

## ✅ 삭제 완료 감지

파일 탐색기에서 단순히 파일을 `Destroy()`하는 것만으로는
Puzzle 03 입장에서 해당 파일이 삭제됐는지 알 수 없다.

따라서 파일이 삭제된 직후 Puzzle 03에 삭제 사실을 전달하도록 연결했다.

```text
FileExplorerWindow
        ↓
파일 삭제
        ↓
DeleteFileDetect()
        ↓
ProgramPathPuzzle
        ↓
PuzzleManager.CompletePuzzle(Puzzle03)
```

이를 통해 **파일 탐색기의 동작과 퍼즐 완료 판정을 분리하면서도 서로 연결**할 수 있었다.

# 🔧 파일 탐색기 문제 수정

Puzzle 03을 파일 탐색기와 연결하는 과정에서
파일 목록 표시와 관련된 문제도 수정했다.

특정 보호용 UI 등에 붙어 있는 `FileBase`까지 일반적인 파일처럼 판단되면서
의도하지 않은 오브젝트가 숨겨질 수 있는 문제가 있었다.

파일 탐색기가 모든 `FileBase`를 무조건 같은 파일로 처리하지 않도록 예외를 추가하면서
목표 파일에 필요한 조건만 적용되도록 정리했다.

# 🎬 Stage 2 Flow 수정

늦은 시간에는 Puzzle 02 이후
**Stage 2가 시작되는 흐름도 수정했다.**

Stage 1의 마지막 시점에서는 이미 메모장이 열려 있다.

그런데 Stage 2가 시작되면서 메모장이 닫히거나
초기 상태로 돌아가면 이전 스테이지와 연결되는 느낌이 끊어진다.

그래서 Stage 2가 시작될 때

```text
Stage 1 완료
    ↓
Stage 2 시작
    ↓
메모장 열린 상태 유지
    ↓
메모장 Focus
    ↓
AI Intro 진행
```

흐름이 되도록 변경했다.

## 🪟 스테이지 사이 UI 상태 유지

이번 작업을 통해 스테이지가 변경된다고 해서
모든 UI가 항상 초기화되어야 하는 것은 아니라는 점을 적용했다.

Stage 1과 Stage 2가 하나의 연속된 게임 흐름이라면

> **이전 스테이지에서 플레이어가 보고 있던 프로그램 상태도 다음 스테이지의 시작 연출 일부가 될 수 있다.**

따라서 공용 메모장은 스테이지가 바뀌어도 유지하고
Stage 2에서 다시 열린 상태로 사용할 수 있도록 했다.

## 🎯 Stage 2 완료 조건 수정

Stage 2에서는 단순히 숨김 항목을 표시했다고 바로 끝나는 것이 아니라
플레이어가 실제 목표 파일까지 열어야 진행이 완료되도록 조건을 정리했다.

즉,

```text
숨김 파일 표시
≠ Stage Clear
```

이며

```text
숨김 파일 발견
    ↓
대상 파일 Open
    ↓
CompleteStage()
```

가 실제 완료 조건이다.

단순한 기능 실행과 **퍼즐의 진짜 목표 달성**을 분리했다.

# 🧩 PuzzleManager 역할 유지

Stage 2 Flow를 수정하면서도
전체 퍼즐 진행을 담당하는 `PuzzleManager` 자체는 수정하지 않는 방향을 유지했다.

각 Stage나 Puzzle은 자신에게 필요한 연출과 조건만 담당하고

```text
개별 Puzzle
    ↓
CompletePuzzle()
    ↓
PuzzleManager
    ↓
다음 Stage
```

처럼 전체 진행 전환은 `PuzzleManager`가 맡는다.

덕분에 Stage 2의 시작 연출을 수정하더라도
전체 퍼즐 관리 구조를 건드릴 필요가 없었다.

## Blender 캐릭터 제작 방법 구체화

Perfectly Legal Magic 캐릭터는
어제 AI 자동 모델링 결과가 원하는 수준에 도달하지 못하면서 직접 제작하기로 했다.

오늘은 직접 모델링할 때 참고할 수 있도록
Blender 캐릭터 제작 과정을 더 구체적으로 조사했다.

특히 캐릭터는 이후 커스터마이징이 필요하기 때문에

* Body
* Hat
* Cape
* Bag

등을 독립적인 파츠로 관리할 수 있도록 만드는 방향을 잡았다.

---

## 🦴 Ragdoll을 고려한 베이스 캐릭터

가장 먼저 제작할 것은 장식이 없는 **기본 Body**다.

기본 캐릭터부터

* T-Pose
* 팔꿈치 위치
* 어깨 위치
* 무릎 위치
* 골반 위치

를 확실하게 잡고,

그 위에 모자나 망토 같은 장식을 추가하는 방식으로 제작해야 한다.

특히 이후 Unity에서 Ragdoll을 적용해야 하기 때문에
외형만 보고 관절을 배치해서는 안 되고

> **실제로 Bone과 Collider를 넣을 위치까지 생각하면서 모델링해야 한다.**

# 📚 Today I Learned

## 1. 퍼즐의 중간 조건과 완료 조건은 구분해야 한다

Puzzle 03에서

```text
경로 완성
```

은 퍼즐을 클리어한 것이 아니라
**삭제해야 할 프로그램을 찾을 수 있게 된 상태**일 뿐이다.

마찬가지로 Stage 2에서도 숨김 파일을 표시한 것과
실제 목표 파일을 연 것은 서로 다른 상태다.

퍼즐을 만들 때

```text
진행 조건
≠
완료 조건
```

을 명확하게 구분해야 한다.

---

## 2. 서로 다른 시스템은 이벤트로 연결하는 것이 편하다

파일 탐색기가 Puzzle 03의 내부 상태를 직접 관리하게 만드는 대신

```text
파일 탐색기
→ 삭제 발생 전달

Puzzle 03
→ 퍼즐 완료 판단
```

처럼 역할을 나누는 것이 더 관리하기 편했다.

파일 탐색기는 **파일을 삭제하는 방법**을 알고
퍼즐은 **그 삭제가 퍼즐 성공인지**를 판단한다.

---

## 3. 게임 진행에는 UI 상태도 포함된다

Stage가 변경될 때 Scene의 오브젝트만 생각하는 것이 아니라

* 어떤 창이 열려 있는가
* 어떤 창이 Focus되어 있는가
* 플레이어가 바로 직전에 무엇을 보고 있었는가

도 게임 진행 상태의 일부가 될 수 있다.

이번 Stage 2에서는 메모장이 열린 상태를 유지함으로써
Stage 1에서 Stage 2로 자연스럽게 이어지도록 만들었다.

---

## 4. 기존 Manager를 건드리지 않고 개별 Flow에서 해결할 수 있다면 그쪽이 안전하다

Stage 2 시작 연출 하나 때문에
전체 `PuzzleManager` 구조를 수정하면 다른 퍼즐에도 영향을 줄 수 있다.

이번에는 Stage 2에만 필요한 동작을 `Stage2Flow`에서 처리함으로써
공통 시스템을 유지하면서 필요한 기능만 변경했다.

---

## 5. 디버깅용 상태값은 퍼즐 제작에서 유용하다

Puzzle 03처럼 여러 조건이 연결되어 있을 때

* `isCorrectPath`
* `isTargetProgramVisible`

같은 상태를 Inspector에서 확인할 수 있으면

```text
입력이 문제인가?
판정이 문제인가?
표시가 문제인가?
```

를 빠르게 구분할 수 있다.

단순히 결과만 보는 것보다
중간 상태를 확인할 수 있게 만드는 것이 디버깅에 도움이 된다.
