# 🪄 Perfectly Legal Magic

## 게임 기획서 재분석

기존 Perfectly Legal Magic의 기획을 다시 검토하면서
단순히 "마법을 사용하는 퍼즐 게임"이 아니라 무엇이 이 게임만의 재미인지 더 명확하게 정리했다.

현재 게임의 핵심은

> **플레이어가 예측 가능한 마법과 환경의 규칙을 이해하고,
> 그 규칙의 빈틈을 이용해서 자신만의 방법으로 문제를 해결하는 것**

이다.

즉 개발자가 준비한 하나의 정답을 찾아가는 것보다
플레이어가 시스템을 실험하면서

> **"이 방법도 되는구나?"**

라는 경험을 만드는 것이 중요하다.

---

## 🧠 재미와 플레이 흐름 분석

게임의 재미를 단순히 보상이나 연출에 의존하는 것이 아니라
플레이어가 직접 가설을 세우고 결과를 확인하는 과정에서 만들도록 방향을 잡았다.

전체적인 재미의 흐름은 다음과 같다.

```text
조건 확인
    ↓
해결 방법 생각
    ↓
마법과 환경을 이용해 빠르게 실험
    ↓
결과 확인
    ↓
게임의 규칙을 다시 이해
    ↓
새로운 방법 시도
    ↓
성공
```

특히 멀티플레이에서는 여기에 다른 플레이어의 행동까지 추가된다.

```text
내가 계획한 행동
        +
친구의 예상하지 못한 행동
        ↓
계획 변경
        ↓
즉석에서 새로운 해결 방법 생성
```

이 과정에서 혼자 플레이할 때와는 다른 상황이 자연스럽게 만들어질 수 있다.

## ⚖️ 게임에서 지켜야 할 핵심 원칙

오늘 기획을 다시 정리하면서 가장 중요하게 잡은 원칙은

> **계획은 망가질 수 있어도, 게임 규칙에 대한 신뢰와 플레이어의 행동권은 망가지면 안 된다.**

는 것이다.

플레이어의 작전이 실패하는 것은 재미가 될 수 있다.

하지만

* 같은 행동인데 결과가 계속 달라지거나
* 왜 실패했는지 이해할 수 없거나
* 게임이 임의로 플레이어의 해결 방법을 막아버린다면

실험하는 재미 자체가 사라진다.

따라서 마법은 최대한 **예측 가능한 규칙**을 가져야 하고,
퍼즐은 그 규칙을 자유롭게 이용할 수 있도록 만들어야 한다.

# 🖥️ UIControllGame

## 📁 파일 탐색기 구현

오늘 UIControllGame에서는 새로운 퍼즐에 사용할 수 있도록
**파일 탐색기 시스템을 실제로 구현했다.**

기존 프로젝트에 존재하는 Window UI 구조를 활용해서
파일 탐색기도 다른 프로그램 창과 동일한 규칙으로 관리할 수 있도록 만들었다.

파일 탐색기 역시 별도의 독립적인 시스템으로 만들어버리는 것이 아니라
기존 Window 시스템 위에서 동작하도록 구성했다.

덕분에 기존에 구현해둔

* Window 관리
* 창 이동
* 버튼 동작
* 프로그램 실행

등을 그대로 활용하면서 새로운 프로그램을 추가할 수 있었다.

## 🧩 Puzzle 02 구현

파일 탐색기 구현과 함께
**두 번째 퍼즐인 Puzzle 02 제작도 진행했다.**

기존에 만들어둔 공통 시스템을 최대한 재사용하면서
Puzzle 02에서는 퍼즐 자체에 필요한 조건만 처리하도록 구성했다.

기본적인 구조는

```text
공통 UI 시스템
    ↓
플레이어 상호작용
    ↓
Puzzle 02에서 조건 확인
    ↓
성공 처리
```

가 되도록 했다.

## 🔄 기존 공통 시스템과 연결

Puzzle 02를 제작하면서 기존에 만들어둔

```text
CopyableUI
    ↓
ClipboardManager
    ↓
DraggableUI
    ↓
DropTarget
    ↓
OnDropSuccess
```

흐름을 실제 퍼즐에서도 활용했다.

복사나 드래그 같은 기본적인 UI 기능을
Puzzle 02 전용으로 다시 만들지 않고 기존 시스템을 그대로 사용했다.

Puzzle 02에서는

> **어떤 데이터가 들어왔는가?**
> **현재 성공 조건을 만족했는가?**

만 판단하도록 역할을 나눴다.

---

## 🎯 퍼즐 판정 방식 정리

퍼즐마다 서로 다른 데이터를 구분할 필요가 있기 때문에
`Object ID`와 `DropTarget`의 조건을 활용했다.

```text
UI 데이터
    ↓
Object ID 확인
    ↓
DropTarget 조건 확인
    ↓
올바른 데이터
    ↓
OnDropSuccess
    ↓
Puzzle 02 성공 판정
```

이렇게 하면 `DropTarget` 자체를 퍼즐마다 새로 구현하지 않아도
서로 다른 퍼즐 조건을 만들 수 있다.

---

## 🔧 구현하면서 해결한 부분

오늘 Puzzle 02를 만들면서
공통 시스템과 퍼즐 전용 로직의 역할을 다시 명확하게 나눴다.

처음부터 퍼즐 하나가

```text
복사
드래그
드롭
판정
연출
완료 처리
```

를 전부 담당하게 만들면
퍼즐이 늘어날수록 비슷한 코드와 설정을 계속 반복하게 된다.

그래서

```text
[공통 시스템]

CopyableUI
ClipboardManager
DraggableUI
DropTarget
Window UI

        ↓

[Puzzle 02]

퍼즐 조건
성공 판정
성공 후 처리
```

처럼 나누는 방식으로 해결했다.

덕분에 Puzzle 02 이후의 퍼즐도
기존 시스템을 조합하고 조건만 새롭게 작성하는 방식으로 제작할 수 있게 됐다.

---

## 📦 퍼즐 Prefab 제작 방식 적용

Puzzle 02 역시 하나의 독립된 퍼즐 단위로 관리할 수 있도록
기존에 정리한

> **퍼즐 하나 = Prefab 하나**

방식을 적용했다.

```text
Puzzle01.prefab
Puzzle02.prefab
Puzzle03.prefab
...
```

개발용 환경에서 퍼즐 하나만 따로 제작하고 테스트한 뒤
완성된 Prefab을 최종 Game Scene에 넣는 구조다.

이 방식으로 작업하면 Game Scene 전체를 건드리지 않고도
각 퍼즐을 독립적으로 개발할 수 있다.

# 📚 Today I Learned

## 1. 프로토타입은 기능을 많이 만드는 단계가 아니다

Perfectly Legal Magic의 기획을 다시 분석하면서
프로토타입에서 가장 중요한 것은 콘텐츠의 양이 아니라

> **내가 생각한 핵심 재미가 실제로 존재하는지 확인하는 것**

이라는 점을 다시 느꼈다.

마법을 10개 만드는 것보다
마법 2개로도 플레이어들이 여러 해결 방법을 만들어낼 수 있는지를 확인하는 것이 먼저다.

---

## 2. 시스템 게임에서는 규칙의 신뢰성이 중요하다

플레이어에게 자유롭게 문제를 해결할 수 있는 권한을 주려면
게임의 규칙부터 확실해야 한다.

플레이어는 실패해도 괜찮지만

> **왜 실패했는지는 이해할 수 있어야 한다.**

그래야 실패한 결과를 바탕으로 새로운 방법을 생각할 수 있다.

---

## 3. 공통 시스템을 잘 만들어두면 콘텐츠 제작 속도가 빨라진다

UIControllGame에서 파일 탐색기와 Puzzle 02를 만들면서
기존 Window와 UI 상호작용 시스템을 재사용할 수 있었다.

처음 공통 시스템을 만들 때는 작업량이 많아 보일 수 있지만
새로운 프로그램과 퍼즐을 추가하기 시작하면 그 효과가 확실하게 나타난다.

---

## 4. 퍼즐 코드는 퍼즐의 규칙에 집중해야 한다

Puzzle 02를 작업하면서

```text
UI를 어떻게 드래그하는가?
```

같은 것은 퍼즐이 알 필요가 없고,

```text
이 데이터가 들어오면 성공인가?
```

같은 부분만 퍼즐이 판단하도록 만드는 것이 더 좋은 구조라는 것을 확인했다.

즉,

```text
공통 시스템 = 상호작용 방법

퍼즐 시스템 = 게임 규칙
```

으로 역할을 나누는 것이 중요하다.
