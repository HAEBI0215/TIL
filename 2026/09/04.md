# 🌐 Multiplayer

## Photon Fusion 기반 멀티플레이 구현

2차 프로토타입에서 최대 4명이 함께 플레이할 수 있도록
Photon Fusion을 이용한 멀티플레이 구현을 본격적으로 진행했다.

현재 구조는 별도의 전용 서버를 운영하기보다는

> **한 명의 플레이어가 Host가 되고 나머지 플레이어가 해당 세션에 참가하는 방식**

을 기반으로 한다.

이를 통해 프로토타입 단계에서는 별도의 서버 인프라를 크게 구축하지 않고도
4인 멀티플레이를 테스트할 수 있도록 했다.

## 🚪 Host / Join 구현

멀티플레이 테스트를 위해 우선

* Host로 방 생성
* 다른 플레이어가 방 참가
* 세션 안에서 플레이어 생성

이라는 기본 흐름을 구현했다.

```text
Host
  ↓
Session 생성
  ↓
다른 Player Join
  ↓
각 Player Object 생성
  ↓
게임 시작
```

이 과정이 정상적으로 동작하면서
멀티플레이의 가장 기본적인 연결 구조를 확보했다.

---

## 👥 플레이어 생성 및 이동 테스트

멀티플레이 세션에 들어온 플레이어마다
각자의 Player Object가 생성되도록 연결했다.

이후 기존에 작성했던 `PlayerController`의

* 이동
* 카메라 회전
* HP / Mana 상태

등의 구조를 멀티플레이 환경에서 사용할 수 있도록 계속 조정했다.

실제로 테스트했을 때 플레이어 이동이 정상적으로 작동하는 것까지 확인했다.

---

## 🎥 로컬 플레이어와 카메라 처리

멀티플레이에서는 모든 Player Prefab이 같은 `PlayerController`를 가지고 있기 때문에
싱글플레이와 다른 문제가 생길 수 있다.

예를 들어 다른 플레이어의

* 카메라
* 마우스 입력
* 이동 입력

까지 자신의 컴퓨터에서 처리하면 안 된다.

따라서 네트워크 게임에서는

```text
내가 조종하는 Player
→ 입력 / 카메라 활성화

다른 Player
→ 네트워크에서 받은 결과만 표시
```

처럼 **로컬 플레이어와 원격 플레이어를 구분하는 처리**가 필요하다는 것을 확인했다.

# 🏠 Room 시스템 개선 방향

현재 테스트에서는 방 이름을 입력해서 세션을 생성하는 구조를 사용하고 있다.

테스트 과정에서 같은 이름으로 방을 생성하는 상황도 확인했는데
기존에 만들어둔 예외처리가 정상적으로 동작했다.

하지만 실제 게임에서는 플레이어가 직접 방 이름을 관리하게 할 필요가 크지 않다고 판단했다.

그래서 이후에는

```text
Host 버튼 클릭
    ↓
방 자동 생성
    ↓
랜덤한 고유 ID 생성
    ↓
해당 ID로 다른 Player 참가
```

방식으로 단순화할 예정이다.

프로토타입에서는 UI보다
**빠르게 친구들과 방을 만들고 테스트할 수 있는 구조**가 더 중요하기 때문이다.

# 🧠 멀티플레이에서 배운 점

## 싱글플레이 PlayerController를 그대로 사용할 수 없다

싱글플레이에서는

```text
Input
 ↓
Player
 ↓
Movement
```

만 생각하면 된다.

하지만 멀티플레이에서는

```text
Input
 ↓
내 Player
 ↓
Network
 ↓
다른 Client에 결과 전달
```

과 같은 과정이 추가된다.

특히 모든 플레이어 오브젝트가 동일한 스크립트를 가지고 있기 때문에
**누가 이 오브젝트를 조작할 권한을 가지고 있는지**를 구분하는 것이 중요하다.

---

## Host 방식에서는 권한 관리가 중요하다

Perfectly Legal Magic은 앞으로

* Fireball
* Levitate
* 물리 오브젝트
* 퍼즐 오브젝트

처럼 물리 상태가 계속 변하는 요소가 많다.

모든 클라이언트가 각자 물리 계산을 하면
같은 오브젝트가 플레이어마다 다른 위치에 존재하는 문제가 발생할 수 있다.

그래서 앞으로는

> **Host가 주요 물리 결과를 판정하고 다른 플레이어에게 결과를 전달하는 방식**

을 중심으로 시스템을 구성하기로 했다.

# 🎨 Character Design

## 플레이어 캐릭터 디자인 구체화

멀티플레이 구현과 함께
Perfectly Legal Magic의 플레이어 캐릭터 디자인도 작업했다.

처음 디자인은 형태가 복잡해서
혼자 Blender로 모델링하고 애니메이션까지 제작하기에는 부담이 있었다.

따라서 디자인을 좀 더 단순하게 수정했다.

### 캐릭터 디자인 조건

* 툰 스타일
* 단순한 실루엣
* 지나치게 많은 장식 제거
* Blender에서 직접 모델링하기 쉬운 구조
* 팔과 다리가 명확하게 분리된 형태
* Ragdoll Physics를 적용하기 좋은 구조

특히 게임에서 물리적인 상황이 자주 발생하기 때문에
캐릭터 역시 래그돌을 적용하기 좋은 형태로 설계하는 것이 중요했다.

---

## 🧍 모델링용 T-Pose 제작

실제 Blender 모델링에 참고할 수 있도록
캐릭터의 기본 디자인을 **T-Pose 형태로 다시 정리했다.**

컨셉 아트만 보고 모델링하는 것보다

```text
정면 형태
+ 
팔 / 다리 비율
+
몸통 구조
```

를 명확하게 확인할 수 있는 T-Pose가
실제 제작 과정에서 훨씬 유용하기 때문이다.

---

## 🪄 마법 지팡이 디자인 수정

캐릭터와 함께 사용할 마법 지팡이도 별도의 모델링 참고 자료로 정리했다.

처음에는 보석이 들어간 형태도 고려했지만
현재 게임의 캐릭터 스타일에서는 불필요하게 복잡하다고 판단했다.

따라서 최종적으로는

> **고전적인 형태의 단순한 나무 마법 지팡이**

방향으로 변경했다.

캐릭터와 마찬가지로
지팡이 역시 직접 모델링하기 쉽고 게임의 툰 스타일에 어울리는 형태를 우선했다.

# 📚 Today I Learned

## 1. 멀티플레이에서는 소유권을 구분해야 한다

같은 Player Prefab을 여러 명이 사용하더라도
모든 플레이어가 같은 입력을 받아서는 안 된다.

**내가 소유한 플레이어만 직접 조작하고, 다른 플레이어는 네트워크 결과를 받아 움직이는 구조**가 필요하다.

---

## 2. 네트워크 물리는 판정 주체가 중요하다

여러 플레이어가 같은 Rigidbody를 동시에 계산하면
각 클라이언트의 상태가 달라질 수 있다.

특히 Perfectly Legal Magic처럼 물리 상호작용이 핵심인 게임에서는
누가 최종 결과를 결정할지 명확하게 정하는 것이 중요하다.

현재는 **Host 중심 판정 방식**을 사용하기로 했다.

---

## 3. 프로토타입 UI는 최대한 단순하게 만드는 것이 좋다

방 이름을 직접 입력하는 기능처럼
테스트에는 필요하지만 실제 게임에서는 불필요한 기능이 존재한다.

따라서 이후에는

**Host → 자동 방 생성 → 고유 ID 발급**

처럼 더 간단한 흐름으로 변경할 예정이다.

프로토타입에서는 완성된 Lobby UI보다
게임의 핵심 기능을 빠르게 테스트할 수 있는지가 더 중요하다.

---

## 4. 1인 개발에서는 디자인도 제작 난이도를 고려해야 한다

멋있어 보이는 캐릭터라도
실제로 모델링, 리깅, 애니메이션까지 혼자 작업하기 어렵다면 현재 프로젝트에는 맞지 않을 수 있다.

그래서 이번 캐릭터는

> **게임의 스타일을 유지하면서 내가 실제로 만들 수 있는 수준까지 단순화하는 것**

을 기준으로 수정했다.
